# Bridge API (GDExtension `CddaSim`)

The DLL `client/bin/fp3d_cdda.windows.x86_64.dll` (loaded by `client/bin/fp3d_cdda.gdextension`) runs CDDA
inside the Godot process on its own thread and registers one class, `CddaSim` (a `RefCounted`). CDDA's state is
global, so every `CddaSim` talks to the same single game. Source: `bridge/src/`; build: `docs/BUILD.md`.

Scripts should not name `CddaSim` as a type (the client must still load when the DLL isn't built): check
`ClassDB.class_exists("CddaSim")` and use `ClassDB.instantiate("CddaSim")`. `client/scripts/live/live_session.gd`
wraps it for the client.

All methods are non-blocking except `stop()`. Everything is polled; there are no signals.

| Method | Returns | Notes |
|---|---|---|
| `start(data_dir, user_dir, world)` | `String` | "" when started, otherwise why not. `data_dir`: absolute, holds `data/json` (the `cdda/` folder). `user_dir`: absolute, made if missing; config, saves and `config/debug.log` go there. `world`: 1-32 of `A-Z a-z 0-9 _ -`; a new world with a random character starts (its name is held to the name input validation of `ui_requests.md` chargen; the same goes for a name the character takes over in play). **An existing world of exactly that name is deleted first if the name starts with `fp3d-` and a start like this made it** (FP3D's throwaway worlds: `--quick`, the tests; boot leaves the file `fp3d_made_this_world.txt` in them; a world of that name without it, a player's or an older FP3D's, is left alone and the game starts in the first free or marked `<name>-2`, `-3`, ... instead); any other name in use, ignoring case, makes the start fail (state `failed`, "world <name> exists"). `start_new_game` refuses new world names starting with `fp3d-` in any case. One game at a time (see Games in one process). |
| `start_load(data_dir, user_dir, world, save)` | `String` | Like `start`, but loads the saved character `save` from the existing `world` (CDDA's main-menu load path). **Deletes nothing.** `world` and `save` must be names `list_worlds` / `list_saves` give for `user_dir`; anything else is refused at once. One game at a time (see Games in one process). |
| `start_new_game(data_dir, user_dir, world, fresh_world, chargen, world_setup = false)` | `String` | `world_setup` (fresh worlds only): ask for the world's settings and mods with a `world_setup` request first. A new game. `fresh_world` true: world `world` is made; never replaces one: a name in use, ignoring case and whether or not `list_worlds` shows it, makes the start fail ("world <name> exists"; the client's MainMenu should refuse taken names first, ignoring case). Nothing is written before the world setup is answered. False: a new character in the existing `world` (a name `list_worlds` gives; nothing deleted). `chargen` true: the character comes from a `chargen` request (ui_requests.md) instead of CDDA's random "play now" one. One game at a time (see Games in one process). |
| `list_worlds(user_dir)` | `PackedStringArray` | Worlds in `user_dir/save/` (folders holding `worldoptions.json` or `master.gsav`), sorted, max 256. Reads the folders directly, so it works before a start. Skips symlinks/junctions and names that aren't plain UTF-8 text or could be paths (`/ \ : * ? " < > |`, leading `.`/space, trailing `.`/space, > 128 bytes). A missing folder gives `[]`; a relative path gives `[]` and an error. |
| `list_saves(user_dir, world)` | `PackedStringArray` | Characters saved in `world` (the save id CDDA shows), sorted, max 256. Only files named `#<CDDA base64>.sav` or `.sav.zzip` whose name decodes to plain text (no control characters, not starting with `#`) and encodes back to the same file. |
| `delete_save(user_dir, world, save, delete_empty_world)` | `String` | Deletes the character `save` (exactly as `list_saves` gives it) from `world`: every file and folder CDDA keeps for it there (`<its save file name without .sav>.<anything>`: log, map memory, seen overmaps, zones, rules, ...), the save file last, so a partial failure leaves it listed. `delete_empty_world` also deletes the world folder when no save file at all is left in it. Links and junctions are removed, never followed; nothing outside `user_dir/save/<world>/` is touched (refused when `user_dir/save` is itself a link; `world` must be a name `list_worlds` gives, in the folder's own spelling). Works before a start, like `list_saves`. "" when done, else why: bad or unlisted names, "not while a game runs" (this process booting or playing), "that world is in use by another game" (another process plays it: a game holds the lock file `user_dir/fp3d_locks/<hex of the name>.lock` until its game thread is done, and a second process can't start that world meanwhile), "could not delete <names>". |
| `stop()` | | Ends the game (no save) and waits until it is over; another may start then. While booting this waits until loading is done (up to ~30 s). The extension calls it on unload. The extension ends the game thread itself on unload. |
| `get_state()` | `String` | `idle`, `booting`, `running`, `ended` (death, abandoning the character, quit, or a cancelled start), `failed` (an exception), `stopped`. A death or an abandoned character ends the game without asking the client anything: none of CDDA's end screens, no deathcam, and a world set to ask what to do once its last character is gone is kept. |
| `get_error()` | `String` | Why it ended or failed: `saved and quit`, `the character died`, `the game ended` (also CDDA's "Abandon this character"), `cancelled` (the client cancelled the `world_setup` or `chargen` request: no error to show; a world this start made is deleted again, only that one and only when no character is saved in it, as it is when the program closes during them), or the exception text (with `(CDDA's last error: ...)` when CDDA logged one). A boot with no progress for 180 s that isn't waiting on the client (character creation, world settings) turns `failed` with `the game stopped booting: nothing moved for 180 s in "<phase>" ...`; the game thread is told to stop, and quitting waits for it at most 10 s. |
| `get_boot_info()` | `Dictionary` | The boot's progress, any state: `phase` ("<phase>" or "<phase>: <step>", e.g. `Loading files: <file>`; at most 300 bytes), `seconds` since the start, `phase_seconds` in this phase, `errors` (CDDA debug messages since the start; never a prompt in FP3D games) and `last_error` (the last one, at most 300 bytes, "" none). Each new phase is also printed to stdout as `fp3d boot <seconds> s: <phase>   [after <previous> (<n> s)]`, and the first 50 CDDA errors as `fp3d: CDDA error: ...`. |
| `get_request()` | `Dictionary` | The pending UI request, `{}` if none. Fields as in `ui_requests.md`: `id`, `kind` (key, menu, popup, string, item_select, item_multi, direction, target, world_setup, chargen, shot, swing, number), `context`, `title`, `text`, `entries` (Array of `{id, label, enabled, description}`), `selected` (menu requests only: the index into `entries` of the entry CDDA highlights, the one its Enter would pick; -1 when no entry is enabled), `actions` (PackedStringArray), `allow_cancel`, `max_len`, `mode`, `status`, `origin`, `cursor` (Vector3i), `range`, `allow_vertical`, `candidates` (Array of Vector3i), `timed`, `turn`, `paused`, `pause_reason`. Target requests add `weapon_wielded` (bool) and, firing a gun, `dispersion` / `dispersion_typical` (float arcmin, only when > 0); shot requests add `shot_error`, `shot_angle` (degrees) and `dispersion` (floats; client-flown shots in `ui_requests.md`), and for a shotgun shell `pellets` (Array of floats, arcmin, at most 32); number requests add `min`, `max` and `default` (ints). Compare `id` to see a new one. |
| `answer(d)` | `bool` | Answers the pending request. `d`: `id` (int, required), optional `cancel` (bool), `action` (String, ≤64 bytes), `entry` (int), `text` (String, ≤1024 bytes), `picks` (Array of `[entry id, count]`, count 0 = all, ≤4096), `pos` (Vector3i), `number` (int, number requests only; the sim checks the range), `shot` (target and shot requests: Dictionary `{end` (Vector3i, required), `hit_uid` (int), `part` (String, ≤64 bytes), `quality` (float, 0..0.99), `fly` (target only; a bool, anything else = false), `pellets` (shot only: Array of at most 32 Dictionaries of the same `{end, hit_uid, part, quality}`, `{}` for a pellet not flown)`}`). Any field of the wrong type → `false` and nothing is sent. Strings lose control characters. A stale `id` is ignored by the sim. |
| `queue_action(action)` / `clear_actions()` / `get_queued_actions()` | `bool` / / `int` | The action queue (`ui_requests.md`): main-loop action names (`UP`, `pause`, `LEVEL_UP`, ...), max 32. |
| `queue_action_at(action, square)` | `bool` | `queue_action` for an action that asks for a square next to the player (`open`, `close`, `examine`, ...): CDDA takes exactly `square` (absolute `Vector3i`), with no `direction` request, and never another square it would pick by itself (its "autoselect the only one" option opens the only openable square nearby when you meant a locked one). A square CDDA doesn't allow for it (not next to the player, locked, nothing there to open) does nothing, with CDDA's message ("There is nothing that can be opened nearby."). An action that asks for no square ignores it. |
| `queue_item_action(d)` | `bool` | One item by its snapshot handle, no menus (see "Single items" below). `d`: `op` ("take", "put", "drop", "unload", "reload", "clear", "throw", "pour", "place", "spot", "hold", "consume", "cook", "light", "extinguish", "mod_add", "mod_remove"), `item` + `type` (uid and itype index from the snapshot, ints; light may leave both out, extinguish never has them), `pos` (Vector3i: the square to take from or drop on, where a put's container or an unload's item lies, where a reload's ammo lies, the square thrown at, the square poured onto, or where an item to consume lies; required for take, drop, throw, place, spot, cook, light and extinguish, used only for what isn't carried), `hand` ("pack" default, "main", "off"; take and unload; hold needs "main" or "off"), `container` + `container_type` (put, required; reload: the ammo or magazine to load with, required; mod_add and mod_remove: the wielded gun, required; pour: the container poured into; take, optional: the container lying on `pos` that holds `item`, one level deep, as the snapshot's `inside` lists it: CDDA's obtain cost (the pocket's own moves) and handling, refused for a sealed or forbidden pocket, someone else's container or item, or an item not directly in it), `pocket` (put and pour into a container, -1 = CDDA's pick, else 0..255 as the snapshot gives it), `spot` (Vector2, each 0..1 across the square; drop and place optional, spot required), `yaw` (int, whole degrees 0..359) and `side` (bool, lies on its side): how the item lies on its spot, only with `spot`, for drop, place and spot; the bridge stores them and gives them back in the snapshot's `poses`, it never reads a meaning into them (the client's convention: yaw counter-clockwise seen from above, 0 = the item's reference axis pointing south; side = its up axis more than 60 degrees off vertical); `shelf` (int 0..15): the furniture shelf, tier or surface the item was put on, in the client's own numbering, only with `spot`, for drop, place and spot; stored like the pose and given back in the snapshot's `shelves`, never read by the sim; `to` (Vector3i, place only, required: the square next to `pos` the item comes to rest on); `tag` (int 1..2^31-1, any op, optional: the client's own number for this action, answered by one `item_result` event when the action has run, see `events.md`; an action dropped from the queue before it ran, by `clear_actions`, the real-time pause when a hostile comes into view or a screen that can't take it, is never answered, so a client times its tags out, e.g. once `get_queued_actions()` is 0 and the next snapshot has come). A missing key, a wrong type or anything out of range (uid 1..2^53−1) → `false`, nothing queued; also false when the queue is full. Unload (CDDA's moves): a gun gives its magazine whole, a magazine its rounds, to `hand`; loaded gunmods come after the item itself, one per action; liquids refused. Reload (CDDA's reload activity and moves): `item` must be carried; loads the first part CDDA's reload menu would offer (the item, the magazine in it, then gunmods), as much as fits; refused with a message when incompatible, the same item, out of reach, sealed, or when the loaded item wouldn't fit where it is. Clear: `item` must be the wielded gun itself (not carried elsewhere, lying around, or inside it); clears its jam (CDDA's `gun_mechanical_simple` faults) with CDDA's mend: the jam's first fix the character can do, its time (10 s for each jam in CDDA's data); refused with a message when not wielded, not jammed, busy, or no fix can be done; `pos`, `hand` and `container` aren't used. Throw (CDDA's throw without its target menu: range, moves, dispersion; one unit of a charges stack): `item` carried, not worn; `pos` a square the character sees, on its level, within throw range, not its own; a held item flies from its hand, anything else needs an empty main hand or a free off hand; refused at a non-hostile NPC. Pour (CDDA's liquid rules): the liquid out of the container `item`, carried or lying on the character's square or one next to it (a pot on its burner; found by its handle there, someone else's is refused), or the carried liquid `item`, to exactly one place: onto `pos` (the character's square or one next to it, all of it), or into `container` (carried, or on or next to the character's square; `pocket` as for put; as much as fits). Pour with both `pos` and `container`, or with neither, or `container_type` / `pocket` without `container` → `false`. Place, spot and hold are for a client that simulates lying items (VR item physics). Place: the client's physics moved the lying item from `pos` onto the next square `to` (same level, one step); no time, no message. The item must lie on the character's square or at most 2 squares from it, on a square the character sees and whose items can be got at; refused for someone else's item, spilt liquid or gas, an item that acts when dropped, one the character couldn't lift, a square that blocks the way (a wall, a closed door or gate, a vehicle's wall), has no floor (open air: falling is CDDA's to do, never free), takes no items (CDDA's NOITEM / SEALED) or has no room; an item moves once a turn (a stack that merges into another stack there takes that one's handle, spot and pose, and that handle has moved too). `spot`, `yaw`, `side` and `shelf` are stored when given and forgotten otherwise. Spot: only how the lying item rests on its square changes; same reach, no time. At most 16 place and spot actions run in one turn, more are refused until the next. Hold: the carried item into the main hand (CDDA's wield and its move cost) or the off hand (its handling cost); refused for a worn item, one in a sealed or forbidden pocket or part of something (a gun's magazine), a liquid or gas, an open container with something in it going from the main hand to the off hand (it would spill), a hand that holds something else (nothing is ever put away to make room), a two-handed item for one hand or while the other hand holds something; a held item goes from one hand to the other when that one is free. Consume (CDDA's eat, drink or first aid, without its menu): `item` carried (a sealed pocket is fine: CDDA opens it) or lying on `pos` where take could get it; when `item` itself isn't something CDDA's consume menu offers, the first thing in it that is (the drink in a bottle; up to 3 containers deep). CDDA's own questions (rotten, allergy, too full, ...) stay real `popup` requests for the player; CDDA's time (its consume activity, or the first aid one) and messages. Refused with a message for what CDDA's menu wouldn't offer: not edible (CDDA's reason, e.g. "That doesn't look edible."), spilt liquid or gas, a medicine the character's body can't use, out of reach. Its `item_result` is done once the activity has started; when the player says no to CDDA's question, or CDDA refuses on its own, it is not done and its text is "" (CDDA's message said why). Works in a shell and while incorporeal, as CDDA's eat does. Cook (L9, CDDA's craft started from a pot's contents): `item` = the container lying on `pos` (the character's square or one next to it), `recipe` (String, required, 1..128 bytes of printable ASCII without spaces, quotes or backslashes: a recipe id a `match_recipes` result for that container listed) and `batch` (int 1..20, default 1); only cook has them. Refused with a message when the recipe isn't one the contents make (or unknown), the batch is more than they hold, the character doesn't know it, lacks a required proficiency, the tools (heat under the pot, or CDDA's crafting inventory; BOIL counts on the emptied pot) or light, morale, is driving, or the pot doesn't lie on a lit heat source (the snapshot's `heat` entry of its square, `lit`); nothing is used up then. Otherwise the components come out of the container only (never from anything else near), the tools are the heat under the pot when it serves (else CDDA's pick, which may ask a `menu`), and the in-progress craft lies at the character's feet (never on the fire, never in the hands; with no room there it is refused before anything is used up), named by the pot's cookware entry (`craft_recipe`, `craft_progress`, contracts/snapshot.md); CDDA's craft activity runs (its time, skill and messages). The craft goes on only while its pot lies on a lit heat source on the character's square or one next to it: when the pot leaves it or the heat goes out, the activity stops with a message and the craft stays where it lies, paused (the same when the player interrupts it). Cook on that pot again with the same `recipe` makes the paused craft go on (`batch` isn't used then; CDDA's checks for going on with a craft); another `recipe` is refused while that craft lies by the character: one craft a pot. While it is worked on, the held state's `activity` is `ACT_CRAFT`; CDDA fast-forwards the activity and no snapshot comes until it ends, stops or asks something. When the craft is done, what it made goes into the pot, as much as CDDA's pocket rules let it hold (a liquid never joins another kind of contents); the rest goes CDDA's own way (at the character's feet; a liquid asks). Its `item_result` is done once the craft has started or gone on. Light (CDDA's fire starting, the firestarter item use without its "Light where?"): `pos` = the square to light, next to the character (never its own); `item` = the carried firestarter (a lighter, matches, ...), or left out for the quickest carried one that works now, as examining a fireplace picks it. CDDA's own questions stay `popup` requests (a fireplace next to the square, a firewood source, a brazier not set up), its time (a quick light, or its fire-starting activity when the fuel is poor) and its charges. Refused with a message when nothing carried lights a fire, the tool has no charges or needs sunlight; when CDDA refuses on its own (already a fire there, the player said no) it is not done, its text is "You weren't able to start a fire." and CDDA's message said why. The fire needs fuel on the square, as in CDDA: `drop` fuel there first. Extinguish (CDDA's "Extinguish fire" of a fireplace): the fire in the fire furniture on `pos` (the character's square or one next to it: a fireplace, wood stove, brazier ...) is beaten out, 200 moves; needs something that bashes, carried or lying near, as in CDDA. No `item`. Refused with a message where there is no fire, or the fire isn't in such furniture (a fire anywhere else isn't put out by hand). Refuelling has no action of its own: `drop` or `put` fuel on the fire's square, `reload` a heat tool; a vehicle's or appliance's heat has no switch in CDDA, it is `lit` while it has power. `recipe` or `batch` on another op → `false`. `to` on another op, a pose or shelf without `spot`, a spot op without `spot`, hold without a hand → `false`. Shares the action queue. |

| `get_events_dropped()` | `int` | Events lost to overflow since start. |

| `get_held()` | `Dictionary` | What the hands hold: `seq` (bumps on every update: before each request but `shot` and once per turn, also during activities), `turn`, `main` and `off` (`{}` when empty, else `uid` (the held item's handle, the same uid the snapshot's carried `items` and `item_states` use; 0 when it has none yet), `id`, `name`, `liquid` ("" none), `ml` and `capacity_ml` (0: not a container)), `activity` (the avatar's activity id, "" none). | `set_cheat(name, on)` | `bool` | Turns a testing cheat on or off for the character (`fp3d/cheats.h`; applied at the main loop's next request, also while paused; message "Cheat <name> on/off."). | `cheat_teleport(pos)` | `int` | The teleport cheat, in any game while cheats are allowed (not only the test range): moves the character to square `pos` (absolute, `Vector3i`) in the reality bubble, or to the nearest free square on that floor within 10 squares. | `cheat_set_weather(id, wind)` | `int` | The weather cheat, in any game while cheats are allowed: the sky holds weather type `id` (one of `get_weather_types()`), now and until changed; `""` gives the weather back to the game (a range game: back to its clear sky). `wind` (float, m/s): 0..45 holds the wind at that speed (more is held at 45; CDDA counts whole mph, so the speed comes back rounded), below 0 (use -1) lets the game decide (a range game holds it still). The temperature is never changed (a range game stays at 20 C). Queued like the range operations, run before the main loop's next request (also while paused); the snapshot's `env` shows the new weather from the next snapshot on, and a lightning storm's flashes come as `lightning` events. Returns the operation's id (outcome in `get_range_info().results`), or 0 when refused before queueing: no game running, cheats not allowed, 32 already waiting, `id` longer than 64 characters or with a character other than a-z, A-Z, 0-9, `_`, `-`, `wind` not a finite number. Refused (the result's `error`): "No such weather." (not a loaded weather type, or "null"), "No such wind.", "This world's weather never changes." (CDDA's eternal weather option), "Not now." (dead or quitting). CDDA saves neither choice: a loaded game decides its weather again. The first one turns that game's achievements off. |
| `cheat_break_grabs()` | `int` | "Break all grabs", in any game while cheats are allowed, with `unstoppable` on or off: every grab on the character and their mount lets go (as `unstoppable` does), done also when nothing held them. Queued like the range operations, run before the main loop's next request (also while paused). Returns the operation's id (outcome in `get_range_info().results`), or 0 when refused before queueing: no game running, cheats not allowed, 32 already waiting. Refused when it runs (the result's `error`): "Cheats aren't allowed." (turned off since it was queued), "Not now." (dead or quitting). The first one turns that game's achievements off. |

Positions are absolute map squares (CDDA `tripoint_abs_ms`, y south), like the snapshot.


### Games in one process

One game at a time. Once it is over (`stop()`, or `get_state()` "ended" or "failed"), any `start*` call may start the next one in the same process, as CDDA's own main menu does: the game thread, CDDA's window, options, fonts and tilesets stay from the first game, so a later start must use the same `data_dir` and `user_dir` (else it is refused: "... used other folders (restart the program ...)"). Between games CDDA's per-game state goes (the map and overmap buffers, zones, the game object, messages, missions, sounds), and so does the bridge's: no request, answer, queued action, query result, event, snapshot (`get_snapshot_seq()` 0), held state, id tables (`get_id_tables_json()` ""), cheats (not allowed) or range info is left from the last game; the clock is turn-based, unpaused, timescale 1. Request ids, query ids and snapshot, held, range and cheat seqs keep counting, so nothing from the last game matches anything in the next. A start while the last game is still closing waits up to 10 s, then is refused ("the last game is still closing"; a boot the watchdog gave up on never closes: restart the program).

## Behaviour to know

- Recipe queries (L9, `cdda/src/fp3d/cooking.h`): the sim answers them at the main loop's request (right after
  the snapshot, and at once when one is posted while it waits there, also while paused) and once per turn
  during activities; one posted during another prompt (a menu, a popup) waits for the main loop. Poll
  `take_query_result` each frame until it gives text. Queries are read-only (nothing in the game changes).
  Result: `{"id": N, "ok": true, "error": "", "container": uid, "matches": [...]}`. Refused: `ok` false, `error`
  one of `out of reach` (not on the avatar's level within CDDA's crafting reach: 6 squares with a clear path, as
  crafting_inventory uses; checked first, so a query can't probe unreachable squares), `not found` (no item with
  that uid **and** itype on that square: gone, moved, or a stale handle), `not a container`, plus `internal` and
  `too large` (shouldn't happen), `matches` empty. Matching uses CDDA's rules: components come **only** from the
  container's contents (its CONTAINER pockets and what's nested in them); tools and qualities from the avatar's
  crafting inventory (what CDDA's craft menu sees in reach: carried, the ground, furniture, vehicles, fires) plus
  the container itself emptied (CDDA counts BOIL only on an empty pot). Only recipes that need heat (a tool of
  CDDA's `surface_heat` / `water_boiling_heat`) and take one of the contents as a component are looked at; a
  recipe matches when every component group is covered by the contents for a batch of 1. Each match:
  `recipe` (id), `result` (itype id), `name` (plain text, ≤ 128 bytes), `batch_max` (largest batch the
  contents cover, ≤ 20), `time_s` (CDDA's time for this character to craft one batch now, game seconds, with
  their crafting speed: light, morale, limbs, pain, helpers), `known` (the character can use the recipe: learned,
  or in a book in reach, or known by a helper, like CDDA's craft menu), `skills_ok` (skill levels the recipe asks
  for), `tools_ok` (tools and qualities there), `missing` (≤ 8 short texts: a missing tool group "fire or
  hotplate or ...", a quality "boiling 1", a skill "cooking 3", a required proficiency), `can_start` (known,
  tools there and required proficiencies; low skill does **not** block it, as in CDDA, where it only adds a
  failure chance). Order: `can_start` first, then the recipes using the most of the contents' kinds, then the
  largest batch, then by id. At most 32 matches.
- Character queries (G4, `cdda/src/fp3d/snapshot.h`): run like recipe queries (same timing, read-only,
  results through `take_query_result`). All text is game data: color tags, line breaks and control characters
  removed; names ≤ 60 columns, descriptions ≤ 400 columns; ids are printable ASCII ≤ 64 bytes (entries with others
  are left out). Result: `{"id", "ok": true, "kind": "character", "name", "profession", "age", "height_cm",
  "weight_g", "weight_max_g", "volume_ml", "volume_max_ml" (what the character carries and can carry, as CDDA's
  inventory screen counts it; ints ≥ 0), "stats": [{"id": "str"|"dex"|"int"|"per", "cur", "base"}], "speed": {"cur", "move_cost", "modifiers": [{"name",
  "value", "percent", "move_cost"}]}, "encumbrance": [{"enc", "layer", "warmth"}], "skills": [{"id", "name",
  "level", "knowledge", "progress", "knowledge_progress", "description"}], "proficiencies": {"known": [{"id",
  "name", "description"}], "learning": [{"id", "name", "percent", "description"}]}, "traits": [{"id", "name",
  "rating", "mutation", "description"}], "bionics": [{"id", "name", "active", "description"}], "power": {"cur_kj",
  "max_kj"}, "effect_descriptions": {effect id: text}, "truncated"}`. Details: speed modifiers as CDDA's speed tab
  lists them (effects by speed name, other speed bonuses, then move cost changes with `move_cost` true; `percent`
  true for a percentage), at most 32. Encumbrance: one per snapshot `body_parts` entry, same order; `enc` is
  clothing, `layer` the layering penalty (CDDA shows "enc+layer"), `warmth` CDDA's warmth number. Skills: every
  skill CDDA's skills tab lists, in its order, at most 64; `level` practical, `knowledge` theory, `progress` and
  `knowledge_progress` 0..100 (%). Proficiencies: at most 64 each; `percent` 0..99. Traits: CDDA's order, hidden
  ones left out, at most 128; `rating` 1 good / −1 bad / 0 neutral (CDDA's point cost), `mutation` false for a
  starting trait. Bionics: one entry per installed bionic, at most 64; power in whole kJ. Effects: the ones the
  snapshot lists (each id once, at most 64). Over 64 KB, descriptions are emptied from the end (effects first, then
  bionics, traits, proficiencies, skills) and `truncated` is true; if that isn't enough (a heavily modded
  character), entries go from the ends of the lists: effects, proficiencies being learned, known ones, traits,
  bionics, speed modifiers, skills. Refused: `{"id", "ok": false, "kind": "character", "error"}` with `internal`
  or `too large` (shouldn't happen).
- Boot takes ~30 s (data load, new game). The first snapshot arrives with the first request.
- Saving: `save_game()`, then watch `get_save_status().done` go up. Or queue the main-loop action `save` (CDDA's "save and quit"); it asks to confirm with a `popup`
  request, answer `action: "YES"`. The game then ends (`ended`, `saved and quit`). `start_load` in a new process
  resumes it: the first request has the saved turn and the player stands where they were.
- A loaded save's world uses its own options and mods; mods CDDA can't find come up as popup requests.
- Hand attacks (first person / VR, `cdda/src/fp3d/hands.h`): main-loop actions `fp3d_attack_main_<DIR>` and
  `fp3d_attack_off_<DIR>`, DIR one of the eight move actions (UP = north). Main hand: CDDA's melee attack with
  what is wielded; off hand: an unarmed strike (the `attack` event's `type` is 0), refused while the wielded item
  needs both hands or the left arm is broken. Nobody there or someone friendly: a message, no time. Nobody next
  to you that way: the main hand's weapon with reach (a spear: 2) strikes the first creature along it, up to its
  reach (CDDA's reach attack, which may hit someone in between). `fp3d_attack_<main|off>_aim_<DIR>` is the same
  strike aimed: the client's crosshair (VR: the hand) is on that creature, so the swing sends one `swing`
  request (`ui_requests.md`); its answer may also call a technique family, and the hit's `attack` event names
  the technique used (`events.md`).
  `fp3d_attack_main_at` / `fp3d_attack_main_aim_at` by `queue_action_at(action, square)`: the main hand at that
  absolute square, e.g. a knight's move off that no way reaches. The fork checks it: this level, not the player's
  square, within the weapon's reach (CDDA's rl_dist, 3 at most), else "That's out of reach." and no time; next to
  you a plain strike, further only a creature the player sees (CDDA's reach attack). No square: "Nothing there
  to hit." The off hand has no `_at` action.
- Held items and context use (`cdda/src/fp3d/held.h`): the off hand (left) holds one carried item, marked with
  the item var `fp3d_offhand` (it stays in its pocket for CDDA's rules; saves keep it; a token the avatar keeps
  too means an item that left the avatar isn't held again on return), empty while the wielded item needs both
  hands or the left arm is broken; an off-hand strike hits with it. Main-loop actions: `fp3d_hold_off` (an
  `item_select` prompt of one-handed items; a message when none fit), `fp3d_stow_off`, `fp3d_use_<DIR>`, first
  that fits: a hose (quality HOSE) in one hand and a container in the other siphon the vehicle on that square
  into the container with no menu (the tank there, else the only one with liquid, else a pick); a held
  container's liquid goes into a vehicle tank there that takes it (refuel); a held container fills from liquid
  there (river, lake, keg, barrel, puddle); anything else is CDDA's examine of that square. A liquid fill (`ACT_FILL_LIQUID`)
  runs one turn per second of wall time in both clock modes, so it can be watched.
- Single items (`cdda/src/fp3d/item_hands.h`, for VR hands, mouse grabbing and looting): the snapshot lists a
  handle (uid) for the first 32 items of each seen pile and for every carried item (`snapshot.md`). The uid is
  kept in the item var `fp3d_uid` (saves keep it; CDDA's stacking ignores it). `queue_item_action` sends one
  action; the sim finds the item again by uid **and** itype **and** square (or that it is carried) and refuses
  with a message (an `m_info` message event, no time spent; place and spot refuse without one, see below) if it
  isn't there, out of reach (your square and the eight around it, same z; place and spot 2 squares) or CDDA says no: "too big", "too heavy", "can't contain liquid", a full main hand,
  someone else's item, a worn item ("Take off ... first"), no room on the square. It never opens a CDDA menu.
  Take: into the inventory (CDDA's best pocket, carry limit as CDDA's pickup), the main hand (CDDA's wield; refused
  while it holds something) or the off hand (held as `held.h`, kept as its own stack). Put: into a carried
  container (worn, wielded, held, or nested) or one lying in reach, CDDA's pocket rules and its parents' limits.
  Drop: on a square in reach; with `spot` the item keeps it in the item var `fp3d_spot` (permille, read back
  strictly and shown in the snapshot) and the message says "put down"; picking it up forgets it. All take CDDA's
  move costs (obtain + move cost). A stack counted by charges (ammo, rocks) moves as a whole; put into a pocket it
  can merge with the same thing and take that stack's uid.
- Gun mods by hand (2026-11-17; `mod_add`, `mod_remove`, both with `tag`; the snapshot's `player.wielded_gun` has
  `mods`, `slots` and `fits`, the id tables `gunmod_location` and `mod_locations`). Only the wielded gun:
  `container` + `container_type` must name it, else the action is refused. `mod_add`: `item` + `type` a carried
  gun mod that isn't in a gun. Refused in CDDA's words when it doesn't fit ("Your Glock 19 doesn't have a slot
  for this mod.", the `fits` reason after the gun's name). The mod that was named is the one installed, also with
  two of a type. CDDA's own questions come as real requests: "Permanently install your X in your Y?" for a mod
  that can't be taken off again, and under 100 % its menu "Attach your X to your Y?" (try without tools, firearm
  repair kit, gunsmith repair kit); answering no or cancelling gives an `item_result` "Never mind.". Then CDDA's
  activity and time (the mod's install time). `item_result` done means the activity started; how it ended (a
  difficult mod can fail and damage the gun) comes with CDDA's message and the next snapshots' `mods`.
  `mod_remove`: `item` + `type` a mod from `mods`. Refused for one that can't be taken off (`mods` flag 1) and
  when CDDA can't unload the mod. When the character couldn't put it back, CDDA's "Are you sure?  You may be
  lacking the skills needed to reattach this modification." comes as a request; no gives "Never mind.". Takes
  half the install time; at the end the mod is in the pack with its uid, or on the ground if it doesn't fit
  (there is no `hand` for it: move it with `take` or `hold` afterwards). Both are refused while an earlier mod
  job on a gun was interrupted and waits unfinished.
- CDDA's debug message prompts and "press any key" screens come as `key` requests with context `RAW_KEY` and no
  actions; answer `action: " "`. The message itself is in `debug.log`.
- CDDA's window still exists, hidden, with SDL's software renderer (B2 tech debt); it is created and destroyed
  on the game thread, which also calls `SDL_Quit()` before it ends (see TASKS.md "Bridge facts"). It loads no
  tileset images: the tile contexts read only a tileset's tile sizes, which the game's view sizes come from.
- The DLL links everything statically (vcpkg `x64-windows-static`, static CRT): it imports only system DLLs.
- `get_snapshot_json` builds the JSON on the calling thread (~tens of ms for 3 levels); call it only when the seq
  changes.
